## 1. Native email notifications — not available today

CAST AI currently delivers alert notifications via a **native Slack integration** or a **custom webhook** (ready-made templates for PagerDuty, OpsGenie, MS Teams, and incident.io). There is no native "send to email" delivery option at this time — this is also stated in our FAQ:
https://docs.cast.ai/docs/logs-alerts-and-metrics#is-it-possible-to-send-alert-notification-to-email-with-cast-ai

## 2. Getting to email anyway — recommended workarounds

Good news: your webhook alert is now configured correctly (request template fixed, category set to **All**, status **Active**), so the CAST AI side is done. To turn that webhook into email, put a small relay behind the callback URL. Common options, easiest first:

1. **Power Automate (Microsoft 365).** Create a flow that starts with the HTTP webhook trigger and ends with the Office 365 Outlook **"Send an email (V2)"** action. Point the CAST AI webhook at the flow URL. You can also add this email step to the Teams workflow you already have, so alerts land in both places. (Note: depends on your tenant policy allowing Power Automate HTTP triggers.)
2. **PagerDuty or OpsGenie.** Both are documented CAST AI webhook targets and both deliver email natively via their notification rules — email with zero custom code, plus on-call scheduling if you ever need it.
3. **Any HTTPS mail relay.** Zapier/Make, an AWS Lambda + SES function, or an internal relay — CAST AI simply POSTs the template-rendered JSON to the callback URL, so anything that accepts the POST can convert it to email.

Setup steps and template variables: https://docs.cast.ai/docs/setup-notification-webhook
Concrete examples (Teams, OpsGenie, Slack): https://docs.cast.ai/docs/examples

**Template gotchas that bit us earlier:** keep the request template exactly as documented for your endpoint type, set `Content-Type: application/json` in the webhook headers, and remember string fields must render strings (use `{{ toEscapedString .Details }}` for description-style fields — otherwise the API rejects the payload with a 422 validation error, which is invisible from the outside except "no alert arrives").

## 3. Testing it end-to-end (your simulation question)

There is no manual "fire a test alert" button in the product today, but you have three practical options:

1. **Validate the downstream endpoint directly.** `curl -X POST <your-endpoint>` with the sample payload from the docs — our guides recommend exactly this before/after wiring CAST AI. It proves everything downstream of CAST AI (relay, email delivery) without waiting for a real event.
2. **Trigger a real notification safely.** On any dev cluster, deploy a test pod that can never be scheduled — e.g. `requests.cpu: "1000"` or a `nodeSelector` matching nothing. It stays **Pending**, CAST AI generates the corresponding alert, and with category **All** it will be delivered. Delete the pod after the test. (This was the test we planned on the call — it only needs deploy access to one namespace on one cluster.)
3. **Cross-check in the console.** Every notification CAST AI generates also appears under the **Notifications** icon in the top navigation, so you can always confirm an event happened even if delivery downstream fails.
