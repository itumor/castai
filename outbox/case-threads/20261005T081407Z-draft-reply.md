## 1. Can the onboarding accept pre-created IAM roles? (castctl)

Verified against the current castctl CLI (checked on both 0.15.0 and the
latest 0.15.1): `castctl cluster connect` **cannot consume pre-existing role
ARNs**. It always creates the IAM objects itself; the only levers are the
**names** of what it creates:

```
--eks-castai-role-name         (default: cast-eks-<cluster>-cluster-role-<id>)
--eks-node-role-name           (default: cast-<cluster>-eks-<id>)
--eks-instance-profile-name    (default: cast-<cluster>-eks-<id>)
--eks-policy-name              (default: CastEKSPolicy-<id>)
```

Reference: https://docs.cast.ai/docs/castctl-reference

Two practical notes:

- castctl is idempotent — if IAM objects already exist under the exact
  resolved names, a re-run adopts them rather than failing. So a
  "create-roles-first-with-our-boundary" flow is possible **by name**, but the
  roles must then carry exactly the permissions and trust from our
  cloud-permissions doc: https://docs.cast.ai/docs/cloud-permissions
- The remaining `iam:CreateRole` step that failed during the meeting belongs
  to the Kvisor volume-stats sync and can be skipped entirely with
  `--kvisor-cloud-storage-sync=false`.
- `--dry-run` prints the full resolved configuration without touching AWS —
  a good validation gate before any real run.

## 2. Alternative onboarding: pre-created roles via Terraform (recommended)

This is the supported path where your team owns IAM role creation. We ship
two public Terraform modules (the same two discussed in the meeting):

1. **`castai/eks-role-iam/castai`** — creates the cross-account role, node
   role and instance profile exactly as CAST AI needs them. Your pipeline can
   run this module alone and attach **your required permissions boundary** to
   the roles, decoupled from onboarding.
2. **`castai/eks-cluster/castai`** — the cluster integration module. When you
   pass it the pre-created ARNs, it creates **no** IAM identities itself:

```hcl
module "castai_eks_cluster" {
  source  = "castai/eks-cluster/castai"
  version = "~> 14.9.0"

  aws_account_id     = "<account-id>"
  aws_cluster_region = "<region>"
  aws_cluster_name   = "<cluster>"

  # Pre-created by your team (or by castai/eks-role-iam/castai):
  aws_assume_role_arn = "arn:aws:iam::<account-id>:role/<your-cross-account-role>"

  node_configurations = {
    default = {
      subnets              = [...]
      security_groups      = [...]
      instance_profile_arn = "arn:aws:iam::<account-id>:instance-profile/<your-profile>"
    }
  }
}
```

Docs: https://docs.cast.ai/docs/terraform-provider
Modules: https://registry.terraform.io/namespaces/castai

Whichever runner executes `terraform apply` still needs role-management
permissions (`iam:CreateRole`, `iam:PutRolePolicy`, instance-profile actions)
scoped to the chosen names — unless your pipeline pre-creates everything via
the role module, in which case the integration run needs no IAM mutations at
all. `sts:GetCallerIdentity` is required for validation (already resolved in
the session).
