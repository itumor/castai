## Evidence summary (all live-fetched 2026-10-09, read-only)

- **[API fact]** `eks.accountId=488305652903` on cluster `7147d0b6` with **empty credentialsId and empty assumeRoleArn** → the value was self-reported at connect time and is *not* assume-role-verified; never refreshed (updatedAt null, reconcile paused).
- **[API fact]** `356676076018` appears on **zero** clusters across **all 130 orgs** visible on the EU API (full enumeration, headers `X-API-Key` + `X-CastAI-Organization-Id`; re-verified by grep of per-org dumps).
- **[API fact]** HAFAS H&O org hosts 13 clusters on 5 distinct AWS accounts; 9 of them (incl. timemachine) on `488305652903` — bulk-onboarded 2026-07-30/31 via console.
- **[Research, castai-openapi.json + k8s-agent repo]** The read-only connect agent discovers the AWS account from the **EC2 instance-identity document (IMDS)** of the node it runs on (auto-discovery), unless `eks.accountId`/`EKS_ACCOUNT_ID` was explicitly set when the install was generated. IMDS cannot misattribute — EKS nodes live in the cluster's own account. Terraform/CI onboarding instead records `data.aws_caller_identity` of the runner.
- **[Research, AWS docs]** CUR `lineItem/UsageAccountId` is the usage/resource-owning account; Wiz attributes by resource ARN, which embeds the true owner account. Both agreeing on 356676076018 makes a reporting artifact unlikely.
- **[AWS-side check, this workstation]** No working credentials for either disputed account (29 profiles, none target them; two reachable accounts have no EKS in eu-central-1). AWS ground truth must come from the customer (one `describe-cluster` call).
- **Audit gap:** no CAST AI audit/event endpoint exists for this cluster's history (`/v1/audit-logs` 404, `/…/events` 501). Whether the 2026-07-31 connect used an explicit account override is only knowable by the internal console/audit team.
