Key reporting principles

1. Avoid double counting — totalSavings == autoscalerSavings; with both autoscalers on, WAS impact is already inside realized savings.
2. Baseline dependency — node-level realized savings require a valid baseline and begin after the baseline period ends; WAS savings are calculated independently of that period.
3. Adoption thresholds — node-level realized savings once ≥20% of nodes are CAST-managed; WAS savings once ≥20% of workloads are managed in VPA mode.
4. Baseline quality — CLUSTER_HISTORY preferred; INDUSTRY_AVERAGE uses fleet-wide assumptions → review unusually high estimates.
5. Missing data is not zero savings — distinguish inactive autoscaling, missing baseline, disconnected agent, unavailable reporting.

Reporting recommendation & docs

Classify each cluster into A–F before aggregation. Report realized node savings separately from WAS-only potential savings; for both-autoscaler clusters show WAS as attribution, not an additional saving.

ⓘ What the columns mean (money · baseline types · agent & flags)

Money columns — one window, one report

WAS $ — savings from Workload Autoscaler right-sizing pod CPU/RAM requests, day by day: (original − current requests) × unit price, CPU + RAM summed. Accrues without any baseline. Field: cost.workloadAutoscalerSavings.
node $ — realized node savings: projected − actual per day, accruing only after the baseline window ends. Field: cost.autoscalerSavings.
total $ — totalSavings == node $ (verified exactly, fleet-wide). WAS savings are already priced into the projection — never add WAS $ + node $. Field: cost.totalSavings.
actual $ — what the cluster actually consumed in the window; the spend these savings sit on. Ratio WAS$÷actual ≈ rightsizing share. Field: cost.actualCost.

Baseline chip — the "no-CAST-AI" counterfactual

Frozen the day node management started (baselinePeriodEndTime): per CPU and RAM an overprovisioning factor (× demand) and a unit-price floor. Needed only for the node track.
Baseline typeHow it is calculatedReliability
CLUSTER_HISTORYUses at least 7 days of the cluster's own history before CAST AI node managementHighest
PEER_CLUSTERSUses historical baseline data from eligible clusters within the same organizationMedium

classic $ · Δ — two savings methodologies, and why they differ

VR total $ (this table's total column) — the value-realization methodology: per day, projected = max(original, current demand) × overprovisioningFactor × max(currentPrice, baselineUnitPrice), CPU + RAM summed; savings = projected − actual, starting after the baseline ends. Baseline-driven, CFO-report methodology. Endpoint: clusters:runValueRealizationReport.
classic $ — the older cost-report methodology. Decomposes savings into two mechanisms per day: downscalingSavings (right-sizing/bin-packing of the node mix) and spotSavings (spot-vs-on-demand price arbitrage). No baseline concept. Endpoint: GET /v1/cost-reports/clusters/{id}/savings?startTime&endTime → summary.totalSavings (string). Observed decomposition, docs-consistent.
Why Δ ≠ 0 (amber when |Δ| ≥ 5% of VR total): ① different cost basis — classic totalCost vs VR actualCost come from different pipelines; ② classic counts spot price arbitrage as savings, VR does not — VR only beats the no-CAST-AI counterfactual price/baseline; ③ VR applies baseline unit-price floors and overprovisioning factors; classic compares node mixes directly; ④ window edges/rounding. Neither is "wrong" — they answer different questions (billing-mix effect vs no-CAST-AI counterfactual).
When classic shows "400 read-only" — Case B: no node management, so classic has nothing to compute; WAS savings live only in the VR report. Report VR numbers for those clusters.
