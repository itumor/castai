# Verification of Karpenter-vs-CAST-AI comparison claims against official CAST AI docs

Date of verification: September 2026. Sources: docs.cast.ai (current Mintlify docs, each page's `updatedAt` noted where relevant), github.com/castai. Verdicts: CONFIRMED / PARTIALLY TRUE / FALSE / NOT FOUND IN OFFICIAL DOCS.

---

## Claim 1 — agent ships cluster state every 15 s; pending pod waits up to 15 s; EC2 API overhead 15–20 s

**Verdict: PARTIALLY TRUE**

- CONFIRMED (15 s sync): "The Cast AI Kubernetes Agent collects all cluster state changes and sends them to the Autoscaler. It uses Kubernetes informers to watch Kubernetes resources and synchronizes all changes to Cast AI at 15-second intervals." — https://docs.cast.ai/docs/autoscaler (updatedAt 2026-07-15)
- NOT FOUND (up-to-15 s pending-pod delay and "15–20 s overhead to EC2 API"): no official page quantifies the pending-pod-to-decision latency this way. The only official end-to-end figure is: "Cast AI is expected to add new Kubernetes Nodes within 60-120 seconds, allowing the Kubernetes Scheduler to schedule all Pending Pods." — https://docs.cast.ai/docs/business-continuity (updatedAt 2026-08-31)
- Supporting context (decision pipeline runs SaaS-side): "1. Watching your cluster state using the Cast AI Kubernetes Agent ... 2. Calculating the required extra cluster capacity ... 3. Evaluating the extra capacity and converting it into optimal node instance types. 4. Provisioning new optimal nodes ..." — https://docs.cast.ai/docs/autoscaler
- Related metric confirming snapshot-based delivery: "castai_autoscaler_agent_snapshots_received_total metric indicates that the Cast AI agent can deliver Kubernetes API changes ("snapshots") to Cast AI SaaS and get a delivery confirmation." — https://docs.cast.ai/docs/business-continuity. The old `autoscaler-architecture` page no longer exists; current equivalent is the "Cluster State Monitoring" section of https://docs.cast.ai/docs/autoscaler.

## Claim 2 — provisioning decision made on CAST AI backend (ML across all customers + live AWS pricing); platform calls ec2:RunInstances via cross-account IAM role; agent never touches EC2

**Verdict: PARTIALLY TRUE (architecture confirmed; "ML models trained across all customers" only documented for Spot features)**

- Decisions are made by the platform, not in-cluster components: the in-cluster agent is read-only — "**Read-only access**: The agent follows the principle of least privilege" (https://docs.cast.ai/docs/about-the-read-only-agent); the Agent's full RBAC is get/list/watch on Kubernetes resources only (https://docs.cast.ai/docs/kubernetes-permissions, "The Cast AI agent's permissions (Read-only)"). In-cluster Cluster Controller "is responsible for handling specific Kubernetes actions, including draining and deleting nodes, adding labels, and approving CSR requests" (https://docs.cast.ai/docs/cluster-controller) — no component documents in-cluster AWS API use.
- ec2:RunInstances via cross-account role CONFIRMED: "When enabling cost optimization for a connected cluster, you grant permissions using a cross-account IAM role. This feature creates a dedicated cluster user in the Cast AI AWS account with a trust policy that can assume the role defined in your AWS account." and the custom policy includes `"Sid": "RunInstancesPermissions", "Action": "ec2:RunInstances"` blocks — https://docs.cast.ai/docs/cloud-permissions (updatedAt 2026-09-22). Also: "Role ARN is printed and sent to the Cast AI console. The platform then uses it to assume the role when making AWS programmatic calls." — https://docs.cast.ai/docs/legacy-onboarding-script
- Live pricing: PARTIALLY confirmed: "Cast AI regularly updates instance type pricing and availability information by querying cloud service provider APIs." — https://docs.cast.ai/docs/autoscaler. The phrasing "live at decision time" is not used; Spot FAQ adds "As Spot Instance availability fluctuates constantly, during the time of instance creation, the particular instance type might not have been available" (https://docs.cast.ai/docs/spot).
- "ML models trained across all of their customers": only confirmed for Spot intelligence: "Cast AI maintains global telemetry across connected clusters to identify which Spot pools have historically stable capacity." — https://docs.cast.ai/docs/karpenter-enterprise (2026-09-14); "Cast AI uses machine learning models trained on historical interruption data to predict Spot Instance interruptions based on near real-time cloud information." — https://docs.cast.ai/docs/ml-spot-interruption-prediction-api. Instance-type selection itself is documented as bin-packing + price sorting ("Filtering the list of all available instance types... Sorting the viable instance types by price. Selecting the cheapest option"), not as an ML model.

## Claim 3 — castai-evictor runs continuously 24/7 (not scheduled); checks all pods fit elsewhere; terminates node; (plus: eviction modes, autoscaler-only?, bin-packing)

**Verdict: CONFIRMED (with documented nuances)**

- Continuous: "Evictor continuously compacts pods into fewer nodes, creating empty nodes that can be removed following the Node deletion policy." and "Evictor returns to the first step, constantly looking for nodes that are good candidates for eviction." — https://docs.cast.ai/docs/evictor (2026-09-10). Cadence: "Evictor continuously scans your cluster every 60 seconds (default cycle time)." — https://docs.cast.ai/docs/downscaling; tunable via `cycleInterval` (default 1m) and `nodeGracePeriodMinutes` (default 5) — https://docs.cast.ai/docs/evictor.
- "checks if all pods on a node could fit elsewhere": CONFIRMED — "Evictor assesses if all current workloads on a candidate node can be rescheduled on existing capacity in the cluster, considering node selectors, affinity rules, and other constraints. If a suitable node is found, Evictor cordons the node, drains it..." — https://docs.cast.ai/docs/downscaling. Note: evictor does NOT use percentage utilization thresholds ("Evictor does not use percentage-based utilization criteria. It considers overall cluster capacity and workload distribution").
- Termination: nodes are deleted via the Node deletion policy, not by Evictor itself: "Once the node is empty after draining, it gets deleted immediately from the cluster via the Node deletion policy (which should be enabled). Node TTL settings do not apply to Evictor-managed node removals." — https://docs.cast.ai/docs/evictor.
- Modes: **Default mode** ("targets every eviction-friendly pod and node in the cluster, whether the nodes were provisioned by Cast AI or not... only considers pods that meet specific safety criteria", multi-replica only), **Aggressive mode** (all replica counts incl. single-replica and Jobs; excludes PVC pods, bare pods, StatefulSets), **Scoped mode** ("restricts Evictor to target only Cast AI-created nodes... only consider nodes for eviction that have the label `provisioner.cast.ai/managed-by=cast.ai`"), all per https://docs.cast.ai/docs/evictor.
- "Evictor ONLY works with the autoscaler": FALSE as a blanket statement. Default mode targets non-Cast nodes too, and docs explicitly cover: soft tainting "in clusters where Evictor operates alongside a third-party autoscaler such as Cluster Autoscaler", and "Clean up Karpenter nodes... applies to clusters running Evictor alongside open-source Karpenter **without** Cast AI for Karpenter" — https://docs.cast.ai/docs/evictor. Privilege: bin-packing is Evictor's core purpose ("a bin-packing component that continuously compacts pods into fewer nodes").

## Claim 4 — eviction protection annotation `autoscaling.cast.ai/removal-disabled: 'true'` supported per-pod AND at namespace level

**Verdict: PARTIALLY TRUE**

- Pod AND Node targets CONFIRMED: "| `autoscaling.cast.ai/removal-disabled="true"` | Node, Pod | Annotation / Label | Evictor won't try to evict a node with this annotation/label or a node running a pod annotated/labeled with this value. |" — https://docs.cast.ai/docs/evictor. Examples: `kubectl annotate pods <pod-name> autoscaling.cast.ai/removal-disabled="true"` and `kubectl label nodes <node-name> autoscaling.cast.ai/removal-disabled="true"`.
- Namespace-level: NOT by annotating a Namespace object (the documented targets are Node and Pod only). Namespace-scoped protection IS supported via Evictor **Advanced Configuration**: podSelector supports a `namespace` matcher with `settings: removalDisabled: enabled: true` — e.g. the documented use case "Marking pods of the `Job` kind in a namespace as `removalDisabled`: `evictionConfig: - podSelector: { namespace: "namespace", kind: Job } settings: { removalDisabled: { enabled: true } }`" — https://docs.cast.ai/docs/evictor.
- Caveats documented: "Protection annotations such as `autoscaling.cast.ai/removal-disabled` only apply to pods that are currently **running**. Once a pod enters a terminal phase (Succeeded, Failed, or Completed), Evictor no longer considers its annotations." — https://docs.cast.ai/docs/evictor. (Related but separate: Workload Autoscaler honors a `workload-autoscaler.cast.ai/ignore` label "on the pod template... or on the namespace" — https://docs.cast.ai/docs/workload-autoscaling-overview; that label affects WOOP mutation, not Evictor.)

## Claim 5 — VPA/rightsizing by castai-workload-autoscaler (WOOP); rightsizing by evicting pod; `vertical.optimization: off` via workloads.cast.ai/configuration; in-place vs eviction

**Verdict: CONFIRMED (with in-place-resize nuance — eviction is the default immediate path, not the only one)**

- Component: "castai-workload-autoscaler dynamically adjusts workload resource requests based on actual usage patterns." — https://docs.cast.ai/docs/hosted-components.
- Eviction-based rightsizing CONFIRMED for immediate mode: "**Immediate mode** (default): The autoscaler evicts pods using the Kubernetes Eviction API. The controller creates replacement pods, and the Cast AI mutating admission webhook applies the updated resource requests at pod creation time. Pod Disruption Budgets are enforced by the Eviction API." — https://docs.cast.ai/docs/workload-autoscaling-overview (2026-09-22). Deferred mode: "never forces pod evictions... webhook applies the recommendation when pods are naturally recreated... On Kubernetes v1.33+ clusters, recommendations may also be applied via in-place resizing without any pod restart."
- Annotation syntax CONFIRMED: annotation key is `workloads.cast.ai/configuration` (YAML value); under `vertical`, "`optimization` ... Enable vertical scaling ("on"/"off"). If using the `vertical` configuration option, this field becomes required." — https://docs.cast.ai/docs/workload-autoscaler-annotations-reference (2026-07-30). Example: `vertical: { optimization: on, applyType: immediate }`. So `vertical.optimization: off` is valid.
- In-place VPA: SUPPORTED — "Cast AI Workload Autoscaler supports Kubernetes in-place resource resizing for clusters running Kubernetes v1.33+, allowing resource adjustments that minimize pod disruption... In-place pod resizing requires Kubernetes v1.33 or later with the `InPlacePodVerticalScaling` feature gate" and "In-place resizing is automatically enabled for eligible workloads when running Kubernetes v1.33+ clusters" (requires WOOP v0.53.0+; falls back to eviction when in-place can't apply) — https://docs.cast.ai/docs/woop-in-place-resizing (2026-09-10).

## Claim 6 — spot-handler: (a) drains on interruption notice vs (b) monitoring-only; k8s terminates; autoscaler provisions replacement

**Verdict: variant (b) CONFIRMED — Spot Handler is monitoring-only and does NOT drain**

- "Spot Handler monitors Spot Instance interruption events from your cloud provider and reports them to the Cast AI platform." and "**Important:** Spot Handler does not take any action on nodes or workloads. It does not: Drain nodes when receiving interruption signals; Initiate pod rescheduling; Perform graceful shutdowns" — https://docs.cast.ai/docs/spot-handler (2026-07-15).
- Handling flow: "1. Spot Handler detects the interruption signal and reports it to Cast AI. 2. The cloud provider terminates the node according to their policies (e.g., GCP provides 30 seconds before termination). 3. Kubernetes handles pod termination using standard procedures. 4. Cast AI's Autoscaler provisions replacement capacity." — https://docs.cast.ai/docs/spot-handler; restated on https://docs.cast.ai/docs/spot: "Spot Handler is monitoring-only—it does not drain nodes, reschedule pods, or take any action on your workloads. When an interruption occurs, Kubernetes handles pod termination using standard mechanisms, and Cast AI's Autoscaler provisions replacement capacity."

## Claim 7 — predictive spot interruption prevention (ML rebalance before signal) and 'Spot Reliability' picking less-interruptible types

**Verdict: CONFIRMED**

- "Cast AI can proactively rebalance spot nodes that are at risk of interruption by the cloud provider... Unlike reactive interruption handling (which waits for cloud provider signals), the interruption prediction model uses machine learning to predict interruptions before they occur. This provides more time for graceful workload migration." — https://docs.cast.ai/docs/spot. "Cast AI's machine learning model can predict that a specific instance will be interrupted within the next 180 minutes. Once a prediction is issued by the model, only the affected instance is cordoned and rebalanced." (same page); predictions run "every 10 minutes for each Spot node", windows: "1 hour for AWS, 3 hours for GCP" (https://docs.cast.ai/docs/ml-spot-interruption-prediction-api).
- Spot Reliability: "**Spot reliability** uses machine learning to select instance types with longer average runtimes. You configure a maximum cost increase percentage, and Cast AI balances reliability against your cost tolerance." — https://docs.cast.ai/docs/spot; config `enableSpotReliability: true, spotReliabilityPriceIncreaseLimitPercent: 20` — https://docs.cast.ai/docs/node-templates.
- Labels applied during handling: `autoscaling.cast.ai/draining=spot-prediction` etc. — https://docs.cast.ai/docs/spot. (AWS Rebalance Recommendations deprecated 2026-07-08 in favor of the CAST AI ML model — same page.)

## Claim 8 — no built-in per-node TTL; forcing replacement requires node_ttl_seconds in a scheduled rebalancing job; meaning of node_ttl_seconds

**Verdict: PARTIALLY TRUE — and `node_ttl_seconds` means "only consider/rebalance nodes OLDER than X" (a minimum-age filter), not "force-replace after X"**

- No Karpenter-`expireAfter`-style per-node TTL exists in the autoscaler. The only autoscaler-side TTL is for **empty** nodes via the Node deletion policy (see downscaling). Evictor drains don't honor TTL at all: "Node TTL settings apply only to nodes that become empty naturally (through job completion or replica scale-down). When Evictor actively drains a node during bin-packing, the node is deleted immediately after draining completes, regardless of the configured TTL value." — https://docs.cast.ai/docs/downscaling.
- node_ttl_seconds semantics (= minimum node age): settings table — "Minimum node age. Amount of time since the node creation before the node can be considered for rebalancing. `0` - means a node of any age can be considered." — https://docs.cast.ai/docs/scheduled-rebalancing. Terraform example explicitly comments: `node_ttl_seconds = 300` with "# only consider instances older than 5 minutes" — same page.
- Official FAQ confirms it IS the documented way to rotate nodes: "You can also set a Node-TTL in a scheduled rebalance job that will automatically rotate out old nodes to pick up the upgrade without the need for a full rebalance." and "You can set the execution time and minimum node age for the scheduled rebalance... 'I want 3 nodes to rebalance if they are older than 7 days every hour between 10 pm and 2 am EST on Saturday and Sunday.'" — https://docs.cast.ai/docs/updates-and-images (FAQ). So functionally: schedule + minimum age ⇒ recurring replacement of nodes older than X — the claim's mechanism is right, the "no per-node TTL" statement is right, but the parameter is a *minimum age* selector for the rebalancing job.

## Claim 12 — WOOP works cluster-wide regardless of provisioner; dual-provisioner (CAST AI autoscaler + Karpenter same cluster) supported?; Kentroller required?

**Verdict: dual-provisioner officially NOT SUPPORTED — Karpenter Enterprise (Kentroller) is the required model for Karpenter clusters; WOOP does operate across Karpenter-managed clusters via that suite**

- Explicit boundary: "**Running Cast AI Autoscaler alongside Karpenter** — Karpenter Enterprise suite is designed for clusters where Karpenter is the sole node provisioner. Running Cast AI's standard node autoscaler and Karpenter together in the same cluster is not supported and will result in undefined behavior." — https://docs.cast.ai/docs/karpenter-enterprise (2026-09-14), section "Unsupported configurations".
- The supported Karpenter model: "the platform deploys Castware components alongside your existing Karpenter installation: Cast AI Agent, Cluster Controller, Kentroller (coordinates Cast AI optimization and automation features with Karpenter), CLM Controller, Spot Handler, Pod Mutator, Workload Autoscaler (handles continuous rightsizing)... Node creation and deletion flow through Karpenter" — https://docs.cast.ai/docs/karpenter-enterprise. Switching from Karpenter Enterprise to the standard autoscaler requires full off-board/re-onboard ("you must off-board the cluster from Cast AI and re-onboard it as a standard EKS cluster" — same page).
- WOOP across provisioners: WOOP operates on workload controllers (Deployments/StatefulSets/DaemonSets/Rollouts/ReplicaSets/CronJobs — https://docs.cast.ai/docs/workload-autoscaling-overview), independent of who provisioned the nodes, and is a component of the Karpenter Enterprise suite itself; conspiracy note: WOOP "relies on the cluster controller to create the recommendation objects" (automated mode). Migration path: one-click import converting NodePools→Node Templates — https://docs.cast.ai/docs/migration-from-karpenter. Also note evictor CAN run alongside open-source Karpenter without Karpenter Enterprise (evictor `karpenterNodeCleanup` option) and autoscaler scoped mode exists for mixed clusters — but *provisioning* by both is what's unsupported.

## Claim 16 — pod-pinner binds pending pods directly to new nodes, bypassing kube-scheduler

**Verdict: CONFIRMED**

- "For pods that need scheduling, Pod Pinner uses the Kubernetes `/pods/binding` API to explicitly assign them to specific nodes by setting `spec.nodeName`. This direct binding bypasses the default Kubernetes scheduling process." — https://docs.cast.ai/docs/pod-pinner (2026-09-22).
- Mechanism: "When the Cast AI Autoscaler determines new nodes are needed... Pod Pinner creates a placeholder Node resource in Kubernetes using the API. This placeholder reserves the space for the incoming node before it physically joins the cluster... When the actual node joins the cluster, it automatically connects to its corresponding placeholder node." (same page). In node-autoscaler/full modes it's deployed at 0 replicas until enabled ("Enable pod pinning" in console); failure is safe ("the default Kubernetes scheduler will automatically take over"). Limitations: incompatible with mutating admission webhooks that alter scheduling specs and with custom resources like GPUs/ENIs.
